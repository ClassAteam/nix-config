# nix-config

Declarative NixOS system + user environment for two machines: the desktop
(migrated from Ubuntu 22.04, GNOME/Wayland, UEFI, on 2026-08-29) and a small
Fornex VPS added on 2026-09-05 as an SSH relay reachable from Russia.

Flake-based since 2026-09-05 (was plain channels before) - see
`../mynotes/nix-config-flake-restructure/` for the full writeup of that
migration and why the VPS host triggered it.

## Layout

    flake.nix                      defines nixosConfigurations.desktop and .vps-relay
    flake.lock                     pinned nixpkgs/home-manager/disko versions
    hosts/
      desktop/
        configuration.nix          system: boot, GNOME, NVIDIA, services, packages
        hardware-configuration.nix generated by nixos-generate-config on that machine
      vps-relay/
        configuration.nix          system: boot, static networking, SSH-only
        hardware-configuration.nix hand-written (generic KVM/virtio) - see note below
        disko.nix                  declarative partition layout, used by nixos-anywhere
    home.nix                       user: dotfiles, bash, git, direnv (home-manager, desktop only)
    dotfiles/                      helix, alacritty, zellij, yazi, gdb configs (linked verbatim)
    pkgs/                          locally-packaged derivations (adguardvpn-cli), shared across hosts

`dotfiles/` files are linked into place by `home.nix`, so they stay editable as
ordinary .toml/.kdl files. Edit, rebuild, done - no translation into Nix syntax.
`home.nix` only applies to `desktop` - `vps-relay` has no user-level config, it's
a single-purpose root-managed box.

**Both hosts' `hardware-configuration.nix` are committed now**, unlike before
the flake conversion. Two independent reasons: (1) each host has its own
directory now, so the original risk this was guarding against - copy-pasting
one machine's hardware config onto another - can't happen by accident anymore;
(2) flakes only see git-tracked files, so a gitignored hardware-configuration.nix
makes `nix eval`/`nixos-rebuild --flake` fail outright, ignored or not.

## Deploying the desktop to a fresh NixOS machine

    # a fresh NixOS install has no git yet - borrow one for the clone
    nix-shell -p git --run 'git clone https://github.com/ClassAteam/nix-config ~/repo/nix-config'
    cd ~/repo/nix-config

    # 1. hardware-configuration.nix is generated per machine - regenerate,
    #    don't reuse the committed one verbatim if the hardware differs
    sudo cp /etc/nixos/hardware-configuration.nix hosts/desktop/hardware-configuration.nix

    # 2. build straight from the flake - no channels, no manual home-manager setup
    sudo nixos-rebuild switch --flake .#desktop

## Deploying vps-relay (or an equivalent fresh VPS)

Not a manual install - `nixos-anywhere` kexecs the target from its stock
image into a temporary NixOS environment, wipes the disk per `disko.nix`,
and installs fresh:

    nix run github:nix-community/nixos-anywhere -- \
      --flake .#vps-relay root@<vps-ip>

Erases the target disk completely - only ever point this at a fresh/disposable
VPS, never a machine holding data you care about. See
`../mynotes/vps-ssh-relay-session/` for the full walkthrough of the actual
Fornex install.

## Per-machine bits

Change these when adding a host:

- add a `hosts/<name>/` directory with its own `configuration.nix` and
  `hardware-configuration.nix`
- add a `nixosConfigurations.<name>` entry in `flake.nix`
- `networking.hostName` inside that host's `configuration.nix`
- `hardware-configuration.nix` - regenerate per machine, never copy between
  machines (`nixos-generate-config --show-hardware-config`), unless there's
  no NixOS system yet to generate it from (e.g. a fresh VPS pre-install) -
  hand-write generic boilerplate in that case, as `hosts/vps-relay/` does.

## If a rebuild fails

Nothing is applied until the build succeeds, so a broken config cannot break a
running system. To back out an applied generation:

    sudo nixos-rebuild switch --rollback

or pick an older generation from the boot menu. For `nixos-anywhere`
specifically: if the install itself fails partway, the target VPS's own
control panel can always reinstall its stock OS from scratch as a fallback -
see the vps-ssh-relay-session docs for why that install carries very little
risk on a freshly rented, empty VPS.
